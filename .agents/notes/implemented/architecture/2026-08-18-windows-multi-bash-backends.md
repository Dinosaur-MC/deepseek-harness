# Agent Note: Windows multi-bash backends — a selector on the single ctx.shell seat

Status: implemented

English | [中文](2026-08-18-windows-multi-bash-backends.zh.md)

## Problem

The shipped harness is bash-first on POSIX and pwsh-only on win32: the base patch disables the bash stack on win32 because bash has no Windows sandbox runner, and the model-facing bash tool stays absent there. Community plugins bridged Git Bash and WSL from outside the repo, duplicating tool logic, hardcoding install paths, and patching official whitelists, while the official seam keeps exactly one `ctx.shell` seat — a second `ShellExecutor` registration throws. Windows users wanted Git Bash and WSL bash usable beside pwsh in one composition, with the model selecting the shell by tool name and the pwsh default preserved.

## Decision

**The tool name is the shell selector.** `dsh-tool-bash` exposes a `defineShellTool({ toolName, shell, dialect })` factory and three fixed instances: `bash` (unchanged, no `shell` field, POSIX), `git_bash` (`request.shell: 'git-bash'`, MSYS dialect), and `wsl_bash` (`request.shell: 'wsl-bash'`, Linux dialect). `dsh-shell-select` occupies the single `ctx.shell` seat and routes `request.shell ?? config.default` to one of its backend instances; `resolve()` stamps the chosen name on the spec as `shellBackend`, `run`/`start` route on it, and an unknown or disabled name throws `SHELL_BACKEND_UNAVAILABLE`.

**Backends are plain instances constructed on child fibers, never rows and never the selector's own fiber.** The vendored Cordis `Service` constructor registers `ctx.reflect.provide(name, …)` immediately ([vendor/cordis/src/service.ts](../../../../vendor/cordis/src/service.ts)), so a second `ctx.shell` registration in the same scope throws `service "shell" has been registered`; `fiber.store` also overwrites by name, so a later-constructed executor would displace the runtime `ctx.shell` resolution. Each backend is constructed on its own child fiber via `ctx.plugin({ inject: ['subprocess', 'sandbox', 'sandboxPolicy'], apply: () => {} })` with `isolate('shell', Symbol(name))` and `isolate('settings', Symbol(name))`. The inject list is load-bearing: a plain `ctx.plugin(() => {})` fiber cannot resolve `subprocess`/`sandbox`/`sandboxPolicy` for the backends, because the get-trap walk requires a fiber in the chain to declare the service — the real-composition loader smoke proved it, and the fix ships with this feature. Isolating `settings` makes the backends' inherited `installSettingsSection` skip silently, because three backends cannot each register the same `shell` settings namespace.

**The `shell` settings namespace belongs to shell-select alone.** A stored settings section layers over the shell-select composition entry, and a committed change rebuilds every backend: the old child fibers are disposed and new backends are constructed from the new partition config, re-probing sandbox availability at first use. `bash-local`/`pwsh-local` need no settings changes.

**base carries no standalone `bash-git`/`bash-wsl` rows.** A row mounting either executor as a plugin would race shell-select for the `ctx.shell` seat, and the isolated realm would hide the wrapper from the tool layer. All backend configuration flows through the shell-select row's `gitBash:`/`wslBash:`/`pwsh:` partitions, so every deployer-visible knob survives. The `pwsh-sandbox` base row is statically `disabled: true` everywhere: on win32 its pwsh backend is held by the selector (behavior unchanged), on POSIX the row is also disabled, and the row stays declared so row identity and dependency remain explicit.

**Executable resolution and sandbox probes are lazy; failures are loud at first use.** Construction never fails. `resolveBashPath`/`resolveWslPath` run at the first routed command and throw an error naming every probed location when Git Bash or WSL is missing; sandbox probes run at the first `sandboxMode` read (the tool layer's apply step, the last moment of composition load) or the first command, and the verdict is cached for the executor lifetime. Explicit `bwrap` mode failing its probe throws the same way at first use. An uninstalled Git Bash or WSL therefore never breaks pwsh in the same composition.

**The auto sandbox contract falls back honestly.** Git Bash `sandbox: auto` probes whether the windows-acl restricted-token runner can launch Cygwin bash; on current hosts it cannot (community-verified), so a failed probe runs commands unconfined and the results carry no sandbox facts. WSL `sandbox: auto` probes `command -v bwrap` inside the distro: a passing probe confines under bwrap with `/` read-only plus `/dev`/`/proc`, `workspace-write` adds the workspace bind and a writable `/tmp` (read-only grants no temp write), a failing probe runs unconfined with honest facts, and explicit `bwrap` failing its probe throws at first use. `danger-full-access` bypasses confinement in both backends.

**wsl.exe commands travel as base64.** The naive `bash -c base64(command)` sketch would make bash execute the base64 text; the shipped argv is `bash -c "echo <b64> | base64 -d | bash"`. The `-c` argument contains only base64 alphabet characters and pipes — no quotes or backslashes — so wsl.exe's Windows→Linux argument serialization cannot corrupt it, and the inner bash's exit code propagates. bwrap profile arguments are passed one per argv element for the same serialization reason, and `--cd` Windows-path conversion is left to wsl.exe.

## Alternatives considered

- **Mount each backend as its own composition row** — every `ShellExecutor` subclass registers `ctx.shell` in its constructor, Cordis throws on the second registration in one context, and the isolated realm would hide the wrapper from the tool layer; only the selector can hold the seat.
- **Construct backends directly on the selector's fiber** — the immediate `Service` constructor registration and the name-overwriting `fiber.store` make a second executor in the same scope either throw `service "shell" has been registered` or displace the runtime `ctx.shell`; the child-fiber split avoids both.
- **Child fibers without an inject list** — the loader smoke showed a bare `ctx.plugin(() => {})` fiber cannot resolve `subprocess`/`sandbox`/`sandboxPolicy` for the backends; the get-trap walk requires the fiber chain to declare them.
- **Fail-fast loading** — eager executable and sandbox probes at construction would make an uninstalled Git Bash or WSL break pwsh on the same host; lazy first-use failure keeps the rest of the composition usable while staying loud.
- **Quote-escaped command arguments through wsl.exe** — wsl.exe's argument serialization damages quotes; the base64 payload is immune because it never contains shell metacharacters.
- **One settings namespace per backend** — three executors cannot register the same `shell` namespace, and per-backend namespaces would fork the user-facing section; shell-select owns the namespace and rebuilds backends on change.

## Consequences

Shipped in this feature: the `bash-git`, `bash-wsl`, and `shell-select` packages with per-file 100% coverage (`pnpm run test:coverage`), the `tool-bash` factory with `git_bash`/`wsl_bash` instances, the base and web-app composition rows, and the win32 standard-preset tool rows. The win32 default route stays `pwsh` ([windows-pwsh-default](../feature/2026-08-01-windows-pwsh-default.md) records the default decision; the [loader disabled-interpolation note](2026-08-11-loader-entry-disabled-interpolation.md) owns the row-gating mechanism), and POSIX compositions keep `bash-sandbox` directly on the seat under the [capability-seams](2026-06-13-capability-seams.md) shape.

The real-composition loader smoke boots the shipped win32 rows through the Loader and self-skips on hosts without Git Bash or WSL; `base.spec.ts` pins the win32 row set and its symmetry with the POSIX rows; CI lanes without Git Bash add `bash-git`/`bash-wsl` to the vitest `windowsUnsupportedPackages` list following the bash-local precedent. The same-PR note covers the shell-select child-fiber inject fix (controller waiver), and the doc gates (`pnpm run doc-sync`: type equivalence, generated catalogs, translation pairing, note format) pin the documented surface.
